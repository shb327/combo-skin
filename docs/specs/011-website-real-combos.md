# 011: The website shows real combos from the API

**Status:** Approved
<!-- Lifecycle: Draft → Approved → Implemented → Audited -->

**Section:** website, api
**Branch:** 011-website-real-combos

## Summary

The website's combos pages show the owner's published combos from the API's public endpoints (spec 009), for glove finishes and, for the first time, knife finishes. The hand-made sample combos and their screenshots go. Until combo screenshots arrive with R2 (spec 012), each card shows the glove and knife finish pictures side by side. The API answers the website's requests with public CORS headers on its public read routes, the only API change.

## Goals and non-goals

**Goals**

- `/gloves/{type}/{finish}/combos` and `/knives/{type}/{finish}/combos` on the website list that finish's published combos, in the API's order, with loading, empty and error states.
- A typed API client generated from `api/openapi.json`, with the API origin from `VITE_API_BASE_URL`.
- A test runner for the website (Vitest, Testing Library, a fake API), run in the `website` workflow.
- Public CORS on the API's public read routes, tested, and checked in the Compose smoke test.
- The sample combos file, its screenshots and code only they used removed, and the made-up "{n} combos" counts gone from the finish cards. The README updated.

**Non-goals**

- Combo screenshots and R2 (spec 012), the 3D viewer, pattern groups, combo variations, prices, the submissions inbox, two-factor login, deployment.
- Real combo counts on the browse and search pages, and a "has combos" filter (Follow-ups).
- Reading the catalog from the API. The website keeps its bundled `catalog.json`.
- A redesign. The combos page keeps its layout, colours, score circle and grid.
- Caching headers on public API responses, and any other API change.

## Context

**Website**

- `website/src/App.tsx`: routes `/gloves/:itemId/:finishId/combos` and `/knives/:itemId/:finishId/combos` both render `Combos`.
- `website/src/pages/Combos.tsx`: finds the finish in the bundled catalog (`getAllGloves` / `getAllKnives`) and shows "Item not found" when it is missing. Glove pages read `getCombosForGlove` from `website/src/data/combos.ts`; knife pages show none (`[] // TODO: getCombosForKnife`). The header line reads "{N} of {M} {knife|glove} combinations available", where M is the number of finishes of the other kind in the catalog. `ComboCard` shows a zoomable screenshot (`react-image-zooom`, used nowhere else), the knife name, the description or "No description available.", the `ScoreCircle` (colour by score: 8.5, 6.5, 5 and 3.5 thresholds) and pattern and float strings whose labels flip with the page's kind. The empty state reads "No combos available".
- `website/src/data/combos.ts`: 4 sample combos for Specialist Gloves | Mogul, with free-text floats and patterns, importing `website/src/assets/combos/mogul/1.jpeg` to `4.jpeg` (spec 003). Nothing else imports it.
- `website/src/assets/combos/glove-1.png` to `glove-9.png` and `knife-1.png` to `knife-9.png` are not combo screenshots: `website/src/components/Hero.tsx` imports them for the home page artwork.
- `website/src/data/catalog.json`: generated by `uv run python -m combo_api.catalog export-website` from the API's snapshot (specs 005, 006), checked by `--check` in the `api` workflow. Active types and finishes only, in display order; each finish has `id` (slug), `name` and `image`. `gloves.ts` and `knives.ts` read it; `vite.config.ts` puts it in its own chunk.
- `website/src/pages/GloveFinishes.tsx` and `KnifeFinishes.tsx` show "{n} combos" in a strip at the bottom of every finish card, where n is the number of finishes of the other kind (576 or 94), not a count of combos. The type cards on `SearchGloves.tsx` and `SearchKnives.tsx` (`ItemCard`) show "{n} available", the type's number of finishes, which is correct. The search dropdown shows no counts.
- `website/package.json`: `dev`, `build`, `lint`, `preview`; no test runner and no API client. `website/.env.example` lists only `DEV_ALLOWED_HOSTS`. `website/index.html` has no Content Security Policy.
- `.github/workflows/website.yml`: `npm ci`, `npm run lint`, `npm run build` and the `/src/` check of spec 003.
- `website/README.md`: describes combos as curated by hand in `combos.ts`, says knife-side combos are not implemented, gives 72 glove finishes (the catalog has 94 since spec 005), and embeds `website/docs/screenshots/combos.png`, which shows the sample cards.
- `npm run build` on `main`: main chunk 360.6 kB (113.4 kB gzipped), catalog chunk 214.6 kB (47.5 kB gzipped).

**API**

- `api/src/combo_api/combos/public_routes.py`: `GET /gloves/{type_slug}/{finish_slug}/combos` (`list_glove_finish_combos`) and `GET /knives/{type_slug}/{finish_slug}/combos` (`list_knife_finish_combos`), tag `combos`. Published combos only, highest rating first; ties in knife order on glove pages and glove display order on knife pages. Each item is `Item` of spec 009: `type_slug`, `type_name`, `finish_slug`, `display_name`, `image_url`, `rarity`, `active`, `float_from`, `float_to`, `seeds`. Unknown finishes return 404 `{"detail": "Not Found"}`. No `Cache-Control` header.
- `api/src/combo_api/main.py`: `AdminCors` sends CORS headers, with credentials, only to the origins in `ADMIN_ORIGINS`; a request from any other origin gets none, so a browser on the website's origin cannot read any response.
- Spec 009 Design (Paths): at deployment the API gets its own subdomain, and its public paths are the same as the website's page paths.
- `.github/workflows/api.yml`: the Compose smoke test checks that `GET /gloves/specialist/mogul/combos` returns `[]`.

**Admin** (for reuse): `admin/scripts/api-types.mjs` generates and checks `src/api/schema.d.ts` with `openapi-typescript`; `admin/src/api/origin.ts` validates `VITE_API_BASE_URL`; `admin/src/api/images.ts` accepts catalog pictures only on the game's image host; since spec 010 server state uses TanStack Query v5; tests use a hand-written fake `fetch`.

**Data checks made for this spec**

- Slugs: the website's `catalog.json` and the API's `snapshot.json` have the same types and finishes with the same slugs in the same order: 8 glove types with 94 finishes and 20 knife types with 576 finishes, with no retired entries. A local API with an imported catalog serves the same lists. Every catalog picture is on `community.akamai.steamstatic.com`.
- A local database with the owner's data has 72 published combos on 4 glove finishes (up to 34 on one), with no float ranges, seeds or descriptions yet.

## Requirements

**Combos pages**

- R1. A glove finish page lists the published combos returned by `GET /gloves/{type}/{finish}/combos`; a knife finish page those of `GET /knives/{type}/{finish}/combos`. Drafts and unpublished combos never show.
- R2. Combos appear in the order the API returns them. The website does not sort them.
- R3. Each card shows: the other item's full name (`<type_name> | <display_name>`: the knife on glove pages, the gloves on knife pages); the rating in the existing score circle; for each item that has them, its float range and its pattern seeds; and the description, if there is one.
- R4. Each card shows the glove finish picture and the knife finish picture side by side where the screenshot was, in a component that a later spec replaces with the combo's screenshot.
- R5. While combos load, the page says so. When the API cannot be reached or fails, the page says the combos could not be loaded and offers "Try again". When the API answers 404, the page says the finish was not found.
- R6. Once combos are loaded, the header line gives their number: "15 combos", "1 combo", and "No combos yet" when there are none. It is hidden while loading and on errors.
- R7. A URL whose slugs are not in the bundled catalog shows the existing "Item not found" page and sends no request to the API.
- R7a. Finish cards on the glove and knife type pages (`/gloves/{type}`, `/knives/{type}`) show no combo count. The type cards' "{n} available" finish counts stay.

**Configuration and code**

- R8. The API origin comes from `VITE_API_BASE_URL`, an exact origin as in the admin (spec 008), with the default `http://localhost:8000`. An invalid value fails the build. `website/.env.example` lists it, commented out, and `website/README.md` documents it.
- R9. The website's API types are generated from `api/openapi.json` and committed; a check fails when they are stale.
- R10. `website/src/data/combos.ts`, `website/src/assets/combos/mogul/`, the `react-image-zooom` dependency and every other piece of code only the samples used are removed. The home page artwork keeps working.
- R11. The website has a test runner; lint, the types check, tests and build run in the `website` workflow.

**API**

- R12. Every response to a `GET` request on the API's public read routes (tags `catalog` and `combos`) carries `Access-Control-Allow-Origin: *` and `Vary: Origin` when the request's `Origin` is not an admin origin. Admin origins keep their CORS headers with credentials on every route, as today. No other route gains CORS headers.
- R13. `api/README.md` documents the public CORS rule.

**Documentation**

- R14. `website/README.md` describes combos coming from the API for both glove and knife finishes, how to see them locally, the new scripts, the current glove finish count, and has a combos screenshot showing real combos.

## Design

| Decision | Chosen | Alternatives rejected, and why |
| --- | --- | --- |
| How the website reaches the API (owner's choice) | Public CORS on the public read routes: `Access-Control-Allow-Origin: *`, no `Access-Control-Allow-Credentials`, for `GET` on routes tagged `catalog` or `combos`, when the `Origin` is not an admin origin. The website calls the API's origin directly, which at deployment is the API's own subdomain behind the same reverse proxy and Cloudflare (spec 009). The website's requests are simple requests (`GET`, no custom headers, `credentials: "omit"`), so no preflight is needed and `OPTIONS` stays as it is. `Vary: Origin` because admin origins get different headers on the same URLs | A dev-server proxy, and one origin in production behind the reverse proxy: the API's public paths are the website's page paths (`/gloves/specialist/mogul/combos` is both), so one origin needs a prefix such as `/api`, which spec 009 rejected (FastAPI's `root_path`, and spec 008's rule that the API base is an origin without a path); a dev proxy also hides CORS until deployment, which spec 008 rejected. A `WEBSITE_ORIGINS` setting listing the website's origins: one more setting per environment for data that anyone can read with `curl`; it only stops other sites' pages from reading it in a browser. Public CORS on the combo routes only: two rules where one covers every public route, and the catalog is the same public data the website already bundles |
| Typed API client (owner's choice) | As in the admin: `openapi-typescript` (dev dependency) generates `website/src/api/schema.d.ts` from `../api/openapi.json`, committed; `npm run api:types` and `npm run api:types:check`; `openapi-fetch` as the runtime client. `website/scripts/api-types.mjs`, `src/api/origin.ts` and `src/api/images.ts` are copies of the admin's files, with the website's paths and names | One shared setup for both apps (a root package or npm workspaces): a new repo-wide structure and a change to the admin for about 80 lines of copied code; revisit if a third app appears. A hand-written `fetch` with hand-written types: nothing tells the website when spec 009's shapes change |
| Server state (owner's choice) | TanStack Query v5, as the admin since spec 010. One `QueryClient` in `main.tsx`. Query key `["combos", kind, type, finish]`; stale after 5 minutes, so going back to a page shows its combos at once; no refetch on window focus; one automatic retry, except after a 404; "Try again" refetches. It adds about 13 kB gzipped to a main chunk of 113 kB | A small hook with `fetch` and `AbortController`: about 40 lines, but it needs its own cache for back navigation, StrictMode's double effect and races when the URL changes, and the counts follow-up adds more queries. SWR: the same trade-off as for the admin, and a second query library in the repo |
| Catalog source (owner's choice) | The bundled `catalog.json` stays the source for search, browse, the page header and finish lookups (R7). Combo cards use the names and pictures in the API's response, which also covers retired items the bundle leaves out. The slugs match (Context) and both come from one snapshot, with `export-website --check` in CI | The API's catalog routes: search would wait for about 30 requests (or a new endpoint) before it works, and every page would depend on the API, for the same data |
| Header count (owner's choice) | The number of combos shown: "15 combos", "1 combo", "No combos yet". Hidden while loading and on errors. With no combos, the header line is the only message: no second "No combos yet" below it | "{N} of {M} combinations available" with M the possible pairings (576 or 94): with about 2,000 combos planned across 670 finishes, almost every finish would look nearly empty. A count of combos per knife or glove type: a summary the cards already give |
| Finish card counts (owner's choice) | The strip with "{n} combos" at the bottom of each finish card in `GloveFinishes.tsx` and `KnifeFinishes.tsx` is removed; the cards keep their picture, name and hover effect. The combo counts follow-up adds real counts back. `ItemCard`'s "{n} available" on the type pages counts finishes and stays | Keeping the possible pairings: wrong once real combos are live. A per-card request for its count: up to 35 requests per page, for numbers the counts endpoint gives in one |
| Card content | Title: the other item's `type_name | display_name`. Score circle and thresholds unchanged; the rating shown as the API's number. Below a divider, as today, one line per value that is set, labelled by its item: "Glove Float:", "Knife Float:" as `from - to` (shortest decimal form, e.g. `0 - 0.01`), "Glove Pattern:", "Knife Pattern:" as the seeds, comma-separated, wrapping. The description as plain text with its line breaks; no line when there is none | Keeping "No description available.": every one of the owner's 72 combos has no description, so every card would say it. Labels that flip with the page kind, as today: the API names each item, so a label can say which one it is |
| Pictures in place of the screenshot | `ComboPictures`, its own component in `src/pages/Combos.tsx` (or beside it), fills the card's `aspect-video` box with the glove picture and the knife picture side by side, `object-contain`, `loading="lazy"`, `referrerPolicy="no-referrer"`, `alt` the item's full name. A picture URL not on the game's image host (`pictureUrl`, as in the admin) leaves its half empty. A comment says spec 012 shows the screenshot there when a combo has one | One picture only: the visitor already sees the page's own item in the header, but the pair is the point. Zoom on the pictures: they are small catalog images; zoom returns with screenshots in spec 012 if wanted |
| States and text | Loading: "Loading combos…". Empty: the header's "No combos yet" only. Not found (404): "This finish was not found." Other failures (no response, 5xx, unexpected body): "Combos could not be loaded." with a "Try again" button. Each in the existing centred box under the header; the header (name and picture from the bundled catalog) shows in every state | One message for every failure: a 404 means the catalog and the API disagree, which a retry does not fix |
| Requests | Only `GET` to the two public combo routes, at the configured origin, with `credentials: "omit"`; slugs come from the bundled catalog entry, not the raw URL (R7). The client refuses a URL outside the origin, as the admin's does | Sending credentials: the public routes read no session, and omitting them keeps the admin's cookie out of every website request |
| Removing the samples | Delete `src/data/combos.ts`, `src/assets/combos/mogul/`, the `react-image-zooom` dependency and the `Combo` and `GloveCombos` types. Move the home page artwork (`glove-1.png` to `knife-9.png`) unchanged to `src/assets/hero/` and update `Hero.tsx`, so `src/assets/combos/` is gone and no folder name suggests combo screenshots | Deleting the whole folder: breaks the home page artwork. Leaving the artwork in `src/assets/combos/`: a misleading name next to real combos |
| Test runner | Vitest with jsdom and Testing Library, the admin's versions and setup, test files next to the code as `*.test.ts(x)`; the API in tests is a fake `fetch` passed to the client, recording each request and answering from responses typed by the generated schema | No tests, as specs 001 and 003 chose: this is the website's first code with states and network behaviour. MSW: one more dependency, as spec 008 found |
| CI | `.github/workflows/website.yml` gains `npm run api:types:check` and `npm test`, before the build. Triggers, permissions and pinned actions unchanged. The `api` workflow's Compose smoke test checks the public CORS header on a combos route and its absence on `/admin/combos` | A separate test workflow: one more badge for the same section |
| API change layout | The public rule lives next to `AdminCors` in `api/src/combo_api/main.py` (or a small module it imports); routes are recognised by their tags, so a new public route tagged `catalog` or `combos` gets the header without another change. Tests in `api/tests/test_cors.py` | A path pattern list: misses or catches routes as paths change |
| Retired items | Shown like the others, with no marker | A "no longer in the game" note: not asked for; the API's `active` flag allows it later |

## API / data model

**API change.** No new route, schema or setting; `api/openapi.json` is unchanged. Response headers:

| Request | Route | Response headers added |
| --- | --- | --- |
| `GET`, no `Origin` or a non-admin `Origin` | tag `catalog` or `combos` | `Access-Control-Allow-Origin: *`, `Vary: Origin` |
| Any method, an admin `Origin` | any | Unchanged (spec 007, 008), plus `Vary: Origin` on the routes above |
| Any other request | any | Unchanged: no CORS headers |

**Website data.** The page reads `PublicCombo[]` from the generated schema (spec 009): `id`, `rating`, `description`, `glove` and `knife` as `Item`. `website/src/data/combos.ts` and its types are removed.

**Configuration** (`website/.env.example`, commented out):

| Variable | Default | Meaning |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `http://localhost:8000` | The API's origin: `http` or `https`, a host, an optional port, nothing else; `http` only for `localhost`. Public: it is built into the bundle |

**Scripts** (`website/package.json`): `test` (`vitest run`), `api:types`, `api:types:check`.

## Security

- S1. Public CORS is limited to `GET` on routes tagged `catalog` or `combos`, never sends `Access-Control-Allow-Credentials`, and never applies to `/admin/` routes, health, docs or the OpenAPI document.
- S2. Admin origins keep exactly their current CORS behaviour; admin session and CSRF checks (spec 007) are unchanged.
- S3. The website sends only `GET` requests, only to the configured API origin, without credentials.
- S4. Combo descriptions and names are rendered as text, never as HTML (`dangerouslySetInnerHTML` is not used).
- S5. Pictures are shown only from `https://community.akamai.steamstatic.com`, without a referrer.
- S6. `VITE_API_BASE_URL` holds no secret; `website/.env.example` shows only the local default, and no hostname of a deployment appears in the repository.
- S7. The `website` workflow keeps read-only repository access, no secrets, `pull_request` (not `pull_request_target`) and SHA-pinned actions.
