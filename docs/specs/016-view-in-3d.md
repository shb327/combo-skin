# 016: View in 3D on the combo cards

**Status:** Implemented
<!-- Lifecycle: Draft → Approved → Implemented → Audited -->

**Section:** website, api
**Branch:** 016-view-in-3d

## Summary

Each combo card on the website gets a "View in 3D" button. Clicking it opens the combo in the owner's 3D viewer, in first person, inside the card where the screenshot is. The viewer gets the same float and seed the screenshot was drawn with (spec 015), so the 3D view matches the card's picture. Nothing 3D loads until the visitor clicks, and closing the view frees its memory. The public API adds each item's game indexes, which the viewer needs and the website does not have today.

## Goals and non-goals

**Goals**

- A "View in 3D" button on every combo card, shown only in browsers with WebGL2. The viewer opens in the card's 16:9 box, with progress, full screen and close.
- The viewer gets the items by definition index and paint index, with the float and seed of the card's screenshot, and the viewer's default agent.
- A warning about the download on phones and small screens before the first 3D view.
- A short message, the screenshot again and, where it can help, "Try again" for every viewer error and for a viewer that never answers.
- `def_index` and `paint_index` on every combo item in the API's responses.
- `VITE_VIEWER_ORIGIN`, the viewer's origin, checked like the website's other origins.

**Non-goals**

- Changes to the viewer, its embed contract or its hosting.
- The dashboard: a 3D preview of a combo on its screenshot agent is a later spec. The dashboard only gets regenerated types.
- The screenshot worker, the screenshot rules of spec 015, and the combo's screenshot agent, which stays admin-only (spec 012).
- Counting 3D opens, and any other analytics (a later spec; this one leaves a hook).
- A Content Security Policy for the website (the cleanup spec; what it needs is in Design).
- Deployment, a lighter 3D mode for phones, a choice of map or agent for visitors, and the follow-ups of earlier specs.

## Context

Specs 001 to 015 are Audited and merged.

**The viewer** (outside this repository, public; contract in [`docs/embed.md`](https://github.com/shb327/cs2-combo-viewer/blob/main/docs/embed.md), protocol version 1)

- Its `/combo` page draws one combo in first person in an iframe, from URL parameters: `knife` and `gloves` (definition indexes), `knife_paint` and `gloves_paint` (paint indexes; `0` or left out for a vanilla knife), `knife_float` and `gloves_float` (required, except a vanilla knife's), `knife_seed` and `gloves_seed` (optional: left out, the viewer draws seed 0, and `cs3d:loaded` echoes the seed drawn), `agent` (left out: Lt. Commander Ricksaw | NSWC SEAL, 5404), `view` (`fp` by default) and `ui` (`0`: only the view and a thin progress bar).
- Events to the parent, each with `type` starting `cs3d:`: `ready` (`version`, `release`, `webgl2`), `progress` (`id`, `loaded`, `total`), `loaded` (`id`, `combo`, `ms`), `error` (`id`, `code`, `message`, `retryable`), `recovering`, `state`. Events caused by the URL's combo carry `id: null`. Commands such as `cs3d:load` and `cs3d:getState` may carry an `id`, echoed in the events they cause.
- Error codes: `no-webgl2`, `bad-params`, `unknown-knife`, `unknown-gloves`, `unknown-knife-finish`, `unknown-gloves-finish`, `unknown-agent` (not retryable); `assets-unavailable`, `context-lost` (retryable).
- It accepts messages only from its parent and only from the site's own origins and `localhost` and `127.0.0.1` on the site's dev and preview ports (5173, 4173) and the dashboard's (5174); it posts only to its parent's origin. Its `frame-ancestors` lets only those pages frame it. It learns the parent's origin from `location.ancestorOrigins`, else the referrer, else the first message, so the host page must not send `no-referrer` to it.
- It checks WebGL2 before fetching its 3D code. It stops drawing while scrolled out of view. A first combo downloads about 34 MB of assets: about 3 s on a fast connection, about 30 s at 10 Mbit/s. Locally its production build runs on `http://127.0.0.1:5321`.

**Website** (specs 011, 013, 014, 015)

- `website/src/pages/Combos.tsx`: `ComboCard` (an `<article>`) shows `ComboPictures`, the other item's name, the score circle and four condition rows. Cards are one column below 1024 px and two above, about 530 px wide at 1440 px.
- `website/src/components/ComboPictures.tsx`: the card's 16:9 box with the screenshot (`srcset` of three WebP versions, `object-cover`, `referrerPolicy="no-referrer"`), or the two finish pictures without one or when it fails to load.
- `website/src/data/catalog.json` (generated by `export-website`, `api/src/combo_api/catalog/export.py`): per type `id`, `name`, finishes; per finish `id` (slug), `name`, `image`. **No definition or paint indexes.** Active items only, so finishes of retired items are missing.
- `website/src/api/schema.d.ts`: a combo item (`Item`) has `type_slug`, `type_name`, `finish_slug`, `display_name`, `image_url`, `rarity`, `active`, `float_min`, `float_max`, `float_from`, `float_to`, `seeds`. **No definition or paint indexes.** It covers retired items too.
- `website/src/api/origin.ts`: `checkOrigin` (an exact origin, plain `http` only for `localhost`) for `VITE_API_BASE_URL` (default `http://localhost:8000`) and `VITE_IMAGE_ORIGIN` (default `http://localhost:9000`), applied in `vite.config.ts` so an invalid value fails the dev server and the build.
- The website has no dialog, no iframe, no `postMessage` and no Content Security Policy. Tests: Vitest with jsdom, Testing Library and a fake API (`src/test/fakeApi.ts`).

**API** (specs 005, 009, 015)

- `api/src/combo_api/catalog/models.py`: `item_types.def_index` (unique) and `finishes.paint_index` (unique per type; 0 for Vanilla). Checked in the snapshot: Karambit 507, Doppler (Ruby) 415, Vanilla 0; Specialist Gloves 5034, Crimson Kimono 10033; no two finishes share a definition and paint index pair.
- `api/src/combo_api/combos/schemas.py` `Item` and `combos/queries.py` `item()`: the combo item of public and admin responses, without indexes.
- `api/src/combo_api/screenshots/inputs.py` `drawn_with`: the screenshot is drawn with float `float_from`, else the finish's `float_min` (null for Vanilla), and seed the lowest of `seeds`, else null ("the viewer's own default"). The job's agent is the combo's screenshot agent or the default agent.
- **Seeds left out.** Most combos have no seeds (none of the owner's first 72), so their screenshot job has `seed: null`. The screenshot worker leaves a null seed out of the viewer's parameters, and the viewer draws seed 0 for it; the website does the same, so the screenshot and the 3D view draw the same pattern.

## Requirements

**The button**

- R1. Each combo card shows a "View in 3D" button when the browser has WebGL2 and the combo can be drawn (R6). Without WebGL2 no card shows it.
- R2. Before the click, nothing of the viewer loads: no iframe, no request to the viewer's origin.

**Opening and closing**

- R3. Clicking the button opens the viewer in the card's 16:9 box. The screenshot (or the finish pictures) stays visible, with a progress bar and "Loading 3D view…", until the viewer reports the combo drawn; then the 3D view shows in its place.
- R4. An open view has "Full screen" and "Close 3D view" controls. Closing, by the button, by Escape while focus is on the page's own controls of the view, by opening another card's view, or by leaving the page, removes the viewer and shows the card as before. At most one view is open on a page.
- R5. Focus moves to "Close 3D view" when a view opens and back to the card's "View in 3D" button when it closes. Loading, ready and error states are announced to screen readers.

**What is drawn**

- R6. The viewer gets both items by the game's definition index and paint index. Each item's float and seed are those its screenshot is drawn with (spec 015): the start of the combo's float range, else the finish's lowest float; the combo's lowest seed, else no seed (the viewer then draws its default, as for the screenshot). A vanilla knife is sent with paint index 0 and no float or seed.
- R7. No agent is sent: the viewer draws its default agent for every combo. The combo's screenshot agent never appears in a public response or in the viewer's address.

**Phones and small screens**

- R8. On a narrow screen (under 768 px), a touch-first device or a browser asking to save data, the first "View in 3D" of a visit shows, in the card's box, that the 3D view downloads about 34 MB, with "Load 3D view" and "Cancel". Nothing loads until "Load 3D view". After one "Load 3D view", later views in the same visit open at once.

**Errors**

- R9. Every viewer error, and a viewer that does not answer in time, removes the viewer, shows the screenshot again and a short message in the card's box. Retryable errors also offer "Try again", which opens the view again.
- R10. A `no-webgl2` error, or a `cs3d:ready` with `webgl2: false`, hides every card's button for the rest of the visit, with "3D isn't available in this browser." on the card that tried.
- R11. An error that says the combo cannot be drawn (bad parameters, unknown item or finish) hides that card's button for the rest of the visit.

**Configuration and API**

- R12. The viewer's origin comes from `VITE_VIEWER_ORIGIN`, an exact origin with the rules of Design. An invalid value fails the dev server and the build, naming the variable. `website/.env.example` and `website/README.md` document it.
- R13. Every combo item in the API's public and admin responses carries `def_index` (its type's definition index) and `paint_index` (its finish's paint index, 0 for Vanilla). The OpenAPI snapshot and both apps' generated types are regenerated. Nothing else in the API changes.

## Design

### The view

| Decision | Chosen | Alternatives rejected, and why |
| --- | --- | --- |
| Where it opens (owner's choice) | Inline, in the card's 16:9 box, over the screenshot, with "Full screen" for a large view (the box's wrapper, so the page's controls stay on it). See the sketch below | A dialog over the page: a larger view at once, but a focus trap, scroll lock and a second layout to build, and it hides the card's name, score and conditions the view is about; on phones the card is already full width. Replacing the whole card: loses the same context |
| Before it is drawn | The iframe sits under the screenshot in the box; the screenshot stays on top until `cs3d:loaded`, as the embed contract advises, with our own progress bar (`loaded / total`) and "Loading 3D view…" along its bottom. The viewer runs with `ui=0`, so its own pill and messages never show | `ui=1`: the viewer's pill would be under the screenshot, and its messages are not ours. Showing the iframe at once: the visitor watches an empty map for up to 30 s |
| One view per page | Opening another card's view closes the open one first. Each view is its own iframe for its whole life | Several at once: about 34 MB of GPU memory each, and browsers drop the oldest WebGL context past a limit. One iframe moved between cards: moving an iframe reloads it anyway |
| Closing | Remove the message listener and timers, point the iframe at `about:blank`, then remove it, so the viewer's WebGL context and memory are released | Hiding the iframe: keeps its memory, against the owner's rule |
| Keyboard and focus | "View in 3D", "Full screen" and "Close 3D view" are buttons. Opening moves focus to "Close 3D view"; closing returns it to "View in 3D". Escape closes the view while focus is on the box's own controls; in full screen the browser's Escape leaves full screen first. Once the visitor clicks into the 3D view, keys go to the viewer's document (cross-origin), which the page cannot hear; the embed has no key forwarding, so Escape there does nothing until focus is back on the page, and "Close 3D view" is always one Tab away. A polite live region says "Loading 3D view", "3D view ready" and the error text | A keyboard trap in the box: worse than the problem. Asking the viewer to forward Escape: a viewer change, out of scope; a possible follow-up |
| Look of the controls (owner's choice) | "View in 3D" sits in the top-right corner of the screenshot, in white at about 60% opacity, to match the screenshots' white watermark at 60% (bottom right; the logo version comes in a later spec). "Full screen" and "Close 3D view" use the same style in the same corner once a view is open. Each has a full-opacity hover and focus state and a visible focus ring, so the controls stay findable on bright renders | A solid button: competes with the screenshot. The bottom-left corner: drafted first; the owner chose the top-right to keep the bottom for the watermark and the progress bar |
| Labels | The iframe's `title` is `<gloves> with <knife> in 3D`, with both items' full names. The button reads "View in 3D", with the same combo name as its accessible description | |
| Leaving the page or the card | Unmounting the card (another page, a new finish) closes its view. Scrolling away leaves it open; the viewer stops drawing while out of view | Closing on scroll: a visitor scrolling back would wait for a reload |
| Counting opens (owner's choice) | A hook only: the view component takes an optional `onLoaded({ comboId, ms })`, called once on `cs3d:loaded`, which the page does not pass in this spec. No request, nothing stored | Counting now: the analytics spec decides what is counted, where, and the privacy wording, all at once |

### What is sent

| Decision | Chosen | Alternatives rejected, and why |
| --- | --- | --- |
| Source of the indexes (owner's choice) | The public combo response: `Item` gains `def_index` and `paint_index`, read from the rows `item()` already loads. Covers retired items, which the bundled catalog leaves out, and adds nothing to the bundle | The website's generated catalog: about 670 more numbers in the catalog chunk, a change to `export-website` and its check, and no indexes for combos whose items are retired (spec 011 shows them). Both: two sources that must agree, for no gain. A server-built `viewer` object with indexes, float and seed: a viewer-specific shape in the public contract, when float and seed follow from fields the response already has |
| Float and seed | `viewerCombo(combo)` in `website/src/viewer/`: float `float_from ?? float_min`, seed the lowest of `seeds`, else left out; a vanilla knife (`float_min === null`, as in spec 013) gets `knife_paint=0` and no float or seed. Floats are sent with `String(number)`, the shortest form that reads back as the same number. Its tests use the cases of spec 015's claim tests, so the two rules cannot drift unnoticed | Sending the middle of the range: spec 015 rejected it for screenshots, and the view must match the screenshot |
| A combo without seeds (owner's choice) | The seed is left out of the address, exactly as the screenshot worker leaves out the job's `seed: null`; the viewer draws seed 0 for it in both cases, so the picture and the 3D view always match. The website never chooses a seed of its own | A fixed seed chosen on the website (drafted as 0): a second place deciding the default, which could drift from the viewer's. A random seed: a different pattern from the screenshot on every open |
| Agent | Not sent: the viewer's default, Lt. Commander Ricksaw \| NSWC SEAL, for every combo. A combo with its own screenshot agent shows different arms in 3D than on its screenshot; accepted, as the agent is admin-only (spec 012) | Sending the combo's agent: it would make the agent public |
| Address | `<VITE_VIEWER_ORIGIN>/combo?` + `URLSearchParams` of `knife`, `knife_paint`, `knife_float`, `knife_seed`, `gloves`, `gloves_paint`, `gloves_float`, `gloves_seed`, `ui=0`, in that order, each left out when it has no value (R6). No `agent`, `view`, `debug` or other parameter | Starting each view with a `cs3d:load` message after `cs3d:ready`: a message posted before the iframe's document is the viewer's is dropped by the browser, so it must wait for the handshake, which only delays the first frame |
| The iframe (sandbox: owner's choice) | Made on click with `src` above, `title` as in Labels, `sandbox="allow-scripts allow-same-origin"` (the viewer keeps its own origin for its asset requests; no popups, top navigation or forms), no `referrerpolicy` attribute (the default, `strict-origin-when-cross-origin`, lets the viewer learn the parent's origin), no `allow` attribute (full screen is requested on the page's own wrapper) | `referrerpolicy="no-referrer"` as on the pictures: older browsers could then not identify the parent until it speaks. No sandbox: the viewer could navigate the top page; there is no reason to allow it |

### Messages

| Decision | Chosen | Alternatives rejected, and why |
| --- | --- | --- |
| Which events are accepted | Only `message` events whose `origin` equals `VITE_VIEWER_ORIGIN` exactly **and** whose `source` is the open view's iframe's `contentWindow`, whose `data` is an object with a known `cs3d:` `type`, and whose `id` is that view's current id (below). Anything else is ignored silently. One listener per open view, added on open and removed on close | Checking the origin only: another card's or a closed view's iframe would be heard. `'*'` anywhere: never |
| Ids | Each attempt is a new iframe, so events for its URL combo carry `id: null` and the iframe's `source` tells attempts apart. On the iframe's `load` event the page sends `cs3d:getState` with a fresh id (`crypto.randomUUID()`), posted to `VITE_VIEWER_ORIGIN`, never `'*'`: it starts the handshake if the viewer could not learn the parent's origin. Events with `id: null` or that id are accepted; `cs3d:state` is used only as a sign the viewer is alive | `cs3d:load` with an id per combo in one long-lived iframe: only useful when one iframe shows several combos, which the one-view rule rules out |
| Stale events | Ignored by the `source` and `id` checks, and by the state machine: once a view has `loaded` or failed, further `progress` is ignored; after close nothing is listened to. `cs3d:recovering` shows "Loading 3D view…" again with the screenshot back on top until the next `loaded` | |
| Time limits | No `cs3d:ready` within 15 s of opening, or, while loading, no event for 60 s: treated as a retryable failure, "The 3D view could not be loaded." | No limit: a viewer that is down, blocked or stalled would leave "Loading 3D view…" forever |
| Error text | Fixed text per code, as text: `no-webgl2` "3D isn't available in this browser." (R10); `assets-unavailable` and the time limits "The 3D view could not be loaded."; `context-lost` "Your graphics card stopped the 3D view."; `bad-params`, `unknown-*` "This combo can't be shown in 3D." (R11); any other code: "The 3D view could not be loaded.", with "Try again" when its `retryable` is true. The viewer's own `message` is not shown | Showing the viewer's `message`: text from another origin on the page, and it is written for debugging ("knife_float 0.5 is outside…") |

### For the cleanup spec (Content Security Policy)

When the website gets a policy, it needs `frame-src <VITE_VIEWER_ORIGIN>` (nothing else from the viewer: its assets load inside the iframe under the viewer's own policy, so `connect-src`, `img-src` and `script-src` need no viewer entry). The site must not send `Referrer-Policy: no-referrer`; the default `strict-origin-when-cross-origin` is right. A `Permissions-Policy`, if added, must keep `fullscreen=(self)`. The viewer's own `frame-ancestors` already limits who may frame it, so no change on its side.

One implementation and one review: the API change is two fields on an existing schema; the website adds one component group with its tests. Smaller than specs 011 and 015.

## Security

- S1. The page accepts viewer events only from `VITE_VIEWER_ORIGIN` and only from the open view's own iframe; it posts to that iframe only with `VITE_VIEWER_ORIGIN` as the target origin, never `'*'`.
- S2. The viewer's iframe is created only on a visitor's click and has `sandbox="allow-scripts allow-same-origin"`: no popups, top navigation or forms.
- S3. Nothing from the viewer is rendered as HTML; error messages are the page's own fixed text, and `dangerouslySetInnerHTML` is still not used.
- S4. The viewer's address carries only the two items' indexes, floats and seeds, and `ui=0`: no combo id, rating, agent or anything about the visitor.
- S5. No public response mentions agents; the new `Item` fields are public game data from the open catalog dataset.
- S6. `VITE_VIEWER_ORIGIN` holds no secret; the repository holds only the local default, and no deployment hostname.
- S7. Nothing about 3D views is stored in the browser or sent anywhere by the page.
- S8. The `website`, `api` and `admin` workflows keep read-only permissions, no secrets and SHA-pinned actions.

## Acceptance criteria

Website checks run in `website/` with Vitest and the fake API; "the fake viewer" is the `MessageEvent` setup of Design. API checks run in `api/` with pytest.

**API**

1. `tests/combos/` public route tests: on both public combo lists, each item has `def_index` and `paint_index` equal to its type's and finish's catalog values (Karambit 507 and Doppler (Ruby) 415, Specialist Gloves 5034 and Crimson Kimono 10033, a vanilla Karambit 0); the admin combo responses carry the same.

## Implementation notes

Built on `016-view-in-3d`, from `main` at the merge of spec 015.

### Deviations

- **Where the visit's state lives (2026-11-08, code layout only).** Design's Code layout puts "one page-level context in `Combos.tsx`" in charge of the open card and the visit's flags. A context inside the combos page is remade on every finish page, so the data warning, "no WebGL2" and "cannot be drawn" would be forgotten on the next finish, against R8, R10 and R11 ("for the rest of the visit"). The state is a reducer in `website/src/viewer/state.ts`, provided once for the app's life by `website/src/Providers.tsx`. The card's box (button, warning, progress, controls and messages) is `src/components/ComboPictures.tsx`; `src/viewer/ComboViewer.tsx` is only the iframe and its messages. The data-saving check sits beside the WebGL2 check in `src/viewer/webgl.ts`. No requirement or behaviour changes.

### Decisions the spec left open

- **Iframe address.** `src` is set by the view's effect, not in JSX, so a remount in React's development double run sets it again after the cleanup's `about:blank`.
- **Handshake id.** `crypto.randomUUID()`, with a `getRandomValues` fallback for a page served over plain `http` on a host other than `localhost` (no secure context there).
- **The hook.** `onLoaded` is called once per attempt, on its first `cs3d:loaded`; a `loaded` after `cs3d:recovering` updates the view but does not call it again.
- **Full screen.** The control shows only where `document.fullscreenEnabled`. It decides between entering and leaving by `document.fullscreenElement` at the click, not by its label, because a browser may report the change late (headless Chrome sometimes sends no `fullscreenchange`; `ComboViewer.test.tsx:250`).
- **Look.** The controls are white text and icons at 60% opacity over a soft shadow, fully white on hover and focus with a white focus ring; icons from `lucide-react`, already a dependency. The data warning dims the screenshot to 40%.
- **Live region.** One `role="status"` `span` per card, always present, so a card without a description still has no `p` element (spec 011's test).
- **Sandbox.** `allow-scripts allow-same-origin` was enough for the hosted viewer: nothing was added.
- **Bundle.** Main chunk 413.31 kB (130.71 kB gzipped), up 4.13 kB gzipped from `main` (126.58 kB); the catalog chunk is unchanged; no chunk-size warning.

### After the audit (2026-11-08)

The first audit (Fail, commit 44fe969) found three blocking differences and some follow-ups, all fixed on the branch with tests:

- **Time limits.** A `progress`, `state` or repeated `ready` after `loaded` restarted the 60 s timer, so a drawn view could be removed a minute later; and any event before `cs3d:ready` replaced the 15 s limit with the 60 s one. `ComboViewer.tsx` now keeps two timers: 15 s from opening, cleared only by `cs3d:ready`; and 60 s between events, only after `ready` and while the combo loads or reloads after `cs3d:recovering`, never once it is drawn (`ComboViewer.test.tsx:516`, `:546`, `:561`).
- **`about:blank` first.** The cleanup ran in a passive effect, after React had removed the iframe. The setup and cleanup are now a layout effect, whose cleanup runs while the iframe is still in the page (`:199`).
- **A refetch while open.** The viewer's address is fixed for the attempt, so a refetched combo with other conditions no longer reloads the open viewer in place (`:219`).
- **Focus when the button is gone.** After "cannot be drawn" or no WebGL2, closing the card's message moves focus to the card's box (`tabIndex={-1}`) instead of the page body (`:439`).
- **Refused full screen.** A refused `requestFullscreen` or `exitFullscreen` is caught and leaves the control as it was (`:306`).
- **Tests.** Criterion 1's test asserts non-empty lists and covers `GET /admin/combos`; criterion 11 covers the data saver fully and the visit's flags on other finish pages (`:349`, `:367`, `:392`).
- **Focus targets recorded.** During the data warning focus is on "Load 3D view" (there is no "Close 3D view" yet); on an error, on "Try again", else "Dismiss".

Re-run on the rebuilt site in headless Chrome against the hosted viewer: the view loads, full screen engages on the card's box and its control reads "Exit full screen", and closing removes the iframe and returns focus. Clicking "Exit full screen" with real input did not register in headless Chrome, whose full-screen viewport (800 by 600) does not match the window it maps input to, so no click reached the page at all; leaving full screen is covered by `:282` and `:294`.

### Follow-ups

- Right after `cs3d:loaded` the screenshot is removed at once; in two captures the box was empty for a moment before the viewer's frame showed. Keeping the screenshot a frame or two longer, or fading it out, would hide that if it shows in real browsers.
- Escape inside the 3D view stays in the viewer's document; a viewer change could forward it (Design).
- The Firefox part of criterion 18.
